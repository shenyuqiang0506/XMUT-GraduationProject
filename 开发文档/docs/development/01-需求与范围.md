# 需求与范围

## 1. 使用场景

学生为社团讲座、项目讨论等活动申请一处场地和若干设备，查看审批进度，必要时取消或加入候补。管理员导入来源资料、维护开放规则、审批并处理学校占用变化。自然语言查询帮助学生找到可行组合，申请人确认后提交正式申请。

一期按“一处场地 + 零到多件设备 + 同一时间区间”建模。每件可移动设备对应独立资源 ID。只有同属一个审批组的资源可以组成申请，审批组可以包含多位授权管理员，首个有效审批结果生效。

## 2. 角色与数据范围

| 角色 | 能力 | 数据范围 |
| --- | --- | --- |
| STUDENT | 查询、申请、取消、候补、消息、AI | 已开放目录；本人申请、候补与对话 |
| RESOURCE_ADMIN | 维护资源与占用、导入、审批、冲突处理 | 其审批组和资源管理范围 |
| SYSTEM_ADMIN | 账号角色、审批组、全局策略、审计 | 全局；写操作仍遵守预约约束 |

第一版提供本地账号，由管理员创建或导入。账号停用后禁止新操作并撤销会话；已有申请保留记录，按业务负责人决定处置。角色变更后服务端重新校验角色与授权，不以客户端按钮显示作为权限依据。

目录与开放规则维护要求该资源的 resource_manager 授权或所属审批组管理员授权；整笔审批要求 approval_group_member 授权。只负责某件设备维护的人员不自动获得整组审批权限。SYSTEM_ADMIN 可进行管理，但仍要执行同样的状态与资源校验。

## 3. 功能清单

| 编号 | 功能 | 验收行为 |
| --- | --- | --- |
| F-01 | 登录、退出、刷新会话 | Web/App 登录态一致，过期和撤销可正确识别 |
| F-02 | 资源目录与筛选 | 按校区、楼栋、类别、容量、设备与可借用范围查询 |
| F-03 | 资源详情与日历 | 展示开放、占用、未知覆盖范围，学生不看到他人敏感申请内容 |
| F-04 | Excel/JSON 导入 | 预览映射与错误；确认后新增/更新；记录来源与批次 |
| F-05 | 开放规则与外部占用 | 维护有效日期与时段；来源占用变化可产生冲突提醒 |
| F-06 | 联合预约 | 检查所有资源，整笔成功或整笔失败 |
| F-07 | 审批 | 统一审批组处理；重复/过期审批不改变状态 |
| F-08 | 取消与过期 | 原子释放关联占用，记录原因，触发候补评估 |
| F-09 | 候补 | 排队、整组暂占、通知、限时确认、取消与过期 |
| F-10 | 通知 | 持久化站内消息、已读、重复事件去重、失败重试 |
| F-11 | AI 查询 | 多轮提取条件、追问、受控查询、展示可核查方案 |
| F-12 | 统计与审计 | 展示按范围统计的申请量、批准/取消/超时等记录 |
| F-13 | 多端支持 | Web 管理；iOS/Android 学生端完成核心流程 |
| F-14 | 外部冲突处理 | 导入新占用后明确标记受影响申请并由管理员处置 |

所有功能纳入最终开发范围，按验收阶段逐项交付。系统离线推送、扫码核销、学校统一身份认证和直接写入学校预约系统属于需另行确认的扩展。

## 4. 数据来源与意义

| 数据 | 来源 | 限制 |
| --- | --- | --- |
| 场地属性 | 学校导出 Excel/JSON | 基本目录不等于实时可预约状态 |
| 可借用标记 | 来源字段加业务负责人确认 | 来源“否”不能自动开放，未知应先核实 |
| 设备、审批组、开放规则 | 管理员确认后维护 | 不能把推测的设备配置当学校实际配置 |
| 课程、考试、临时占用 | 管理方提供或已确认范围的导出 | 必须保存来源、覆盖区间和更新时间 |
| 申请、审批、候补 | 本平台正常操作 | 只表示平台内活动安排 |
| 开发样例 | 明确标记的演示环境 | 与实际学校记录分开，结果说明测试范围 |

已检查样本：Excel 3 条/17 列；JSON 本页 100 条，报告总数 1,132。JSON 本页全部 `sfkjy=否`；Excel 3 条全部可借用。`dateDigitSeparator` 尚未确认是否来自查询条件，不用于独立判定空闲。

## 5. 可用状态

| 状态 | 含义 | 用户操作 |
| --- | --- | --- |
| AVAILABLE | 开放且权限允许，覆盖已确认，当前没有有效冲突 | 可以提交，但提交时重新检查 |
| BUSY | 学校占用、平台暂占或已批准占用 | 展示替代方案或进入候补 |
| CLOSED | 停用、来源不可借用、规则不开放 | 提示原因，不开放申请 |
| UNKNOWN | 覆盖不足、过期或来源含义未确认 | 提示需核实，真实模式下不自动提交 |

可用状态是某个用户、某个时间和某个数据模式下的结果。基础目录可以查询，但只有满足条件的范围开放预约。

## 6. 配置项

以下键必须有来源明确的配置值；学校实际值待确认。

| 配置键 | 意义 | 约束 |
| --- | --- | --- |
| `pendingApprovalTtlMinutes` | 待审批暂占长度 | 正数；到期不能超过活动开始时间 |
| `waitlistOfferTtlMinutes` | 候补收到名额后的确认长度 | 正数；必须留出后续审批时间 |
| `bookingLeadMinutes` | 最晚提前申请时间 | 非负，提交与候补提升时检查 |
| `cancelLeadMinutes` | 学生取消已批准申请的提前量 | 非负；管理员处置另走管理接口 |
| `maxBookingDaysAhead` | 最远预约范围 | 正数；默认不开跨覆盖范围查询 |
| `maxDurationMinutes` | 活动最大时长 | 正数；与开放规则一起校验 |
| `maxActiveApplicationsPerUser` | 用户同时有效申请上限 | 正数；并发时在事务内检查 |
| `coverageFreshnessMinutes` | 占用来源的有效时长 | 正数；超过后转 UNKNOWN |

一期不支持跨自然日预约，时间换算以 Asia/Shanghai 判断自然日。如需跨日，须同步修改规则、日历、检索和测试契约。

有效申请配额计算 PENDING_APPROVAL、APPROVED、CONFLICT_REVIEW 的申请，加上 OFFERED 候补；WAITING 候补不占配额。候补确认时排除正在转移的本条 OFFERED，避免重复计数。增加配额的申请和候补提升必须锁定 applicant_guard，减少配额的终态变化可并发但不能造成计数增加。

## 7. 业务确认清单

| 问题 | 建议草案 | 状态 |
| --- | --- | --- |
| 资源范围 | 一个学院/审批组内的一批资源 | 待确认 |
| 待审批占用 | 有限时暂占全部资源 | 待确认 |
| 联合审批 | 一个审批组审批整笔 | 待确认 |
| 候补排序 | 同组内按提交时间和 ID 排序 | 待确认 |
| 不同候补组 | 不承诺全局 FIFO | 待确认 |
| 新学校占用冲突 | 标为 CONFLICT_REVIEW，由管理员处理 | 待确认 |
| 真实模式覆盖不足 | 阻止自动预约，保留人工核实入口 | 待确认 |
| 双端交付形式 | 两个平台分别运行与留存演示 | 待确认设备与签名方式 |

“待确认”不得写成学校已实行的制度。更新规则要提高策略版本，并记录哪一版本用于每笔申请。
