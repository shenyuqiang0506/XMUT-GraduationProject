# M4 候补与消息

日期：2026-10-13。承接 [M3 联合预约](19-M3联合预约闭环.md)，新增固定组合候补、整组确认机会、可靠消息投递、独立通知服务及 Web 页面。本阶段使用本机 dev 的真实 MySQL、Redis、RabbitMQ、Nacos；学校数据和预约制度仍由用户提供，不自动创建 REAL 策略。

## 1. 候补行为

学生、教师可以登记一处场地与若干单件设备的固定组合。服务端规范化资源主键、UTC 毫秒区间和 REAL/DEMO 模式，生成候补组索引；命中后再次核对完整组合。时间、人数、设施、来源覆盖、开放规则和审批组检查与普通申请共用。全部条件有效，且至少一个成员已被占用或同组已有有效队列时可以候补；空闲且无队列的组合返回 WAITLIST_NOT_NEEDED，覆盖未知不能借助排队绕过检查。已有队列时仍遵守同组 FIFO，后来的申请人不能因暂时空闲越过队首。

| 状态 | 资源占用 | 处理 |
| --- | --- | --- |
| WAITING | 无 | 同组按 created_at、id 排队，不计入有效申请配额 |
| OFFERED | 全组 HOLD | 有确认期限，计入申请人配额，仅本人确认或取消 |
| CONFIRMED | 转交新申请 | 原子创建 PENDING_APPROVAL 申请并转移全组占用，仍须审批 |
| EXPIRED / CANCELLED | 整组 RELEASED，或原本无占用 | 保留候补历史、审计和事件 |

候补不能自动替换设备、时间或场地。不同组合之间没有全局 FIFO 保证。同组有效 WAITING/OFFERED 存在时，直接创建相同组合返回 WAITLIST_PRIORITY；部分资源重叠的不同组仍按数据库实际占用竞争。

后台评估在事务外向身份服务查询当前资格，再获取共同写锁并重读队首。永久不符合资格的队首过期；临时配额不足、资源仍冲突或可信覆盖未恢复时保留队首，不越过它提升后面的用户。账号停用与预约提交分属两个数据库，不承诺跨库原子撤销；不会缓存后台授权结论。

确认重新核验当前策略、配额和整组条件，配额排除本人的当前 offer，避免转换时重复计数。offer 截止不晚于活动开始减当前提前量，也不晚于候补最初截止。到期确认提交过期与释放后返回 409 OFFER_EXPIRED；版本已经被另一操作更新时返回 VERSION_CONFLICT。来源、目录或开放规则变更使 OFFERED 不再有效时，在原写事务内过期并释放全组。

写入顺序沿用 M3：幂等行 → booking_write_guard → 增额时 applicant_guard → 升序关联资源 → 候补组/候补或申请。全局协调行仍串行化业务写入，本次没有吞吐压测。提交后的释放事件仅辅助唤醒，周期扫描轮转组 ID，重启丢失唤醒仍可补偿。默认启动后 3 秒，每秒评估；单条到期失败不阻断其他到期记录。

## 2. 接口与 Web

基础路径 `/api/v1`。业务 ID 使用字符串，时间必须有偏移，最多毫秒精度。候补写入携带 Idempotency-Key；版本动作必须传 expectedVersion。读写均设置 Cache-Control: no-store。

| 方法 | 路径 | 输入和权限 |
| --- | --- | --- |
| POST | `/waitlists` | 学生/教师；与申请 Create 相同：活动、人数、时间、venueId、equipmentIds、requiredFeatures |
| GET | `/waitlists` | 本人列表，status/page/size |
| GET | `/waitlists/{id}` | 本人、原审批组当前授权管理员或系统管理员；越界 404 |
| POST | `/waitlists/{id}/confirm` | 本人且仍有学生/教师资格；expectedVersion，可选 reason |
| POST | `/waitlists/{id}/cancel` | 本人；expectedVersion，可选 reason |
| GET | `/notifications` | 本人收件箱；unreadOnly/page/size，返回 unreadCount |
| POST | `/notifications/{id}/read` | 只标记本人通知；自然幂等，重复保留原 readAt |
| GET | `/admin/outbox` | SYSTEM_ADMIN；status/page/size，仅返回投递摘要 |
| POST | `/admin/outbox/{id}/retry` | SYSTEM_ADMIN；FAILED、expectedVersion、非空 reason、幂等键 |
| GET | `/admin/notifications/dead-letters` | SYSTEM_ADMIN；最多预览 20 条元数据，不暴露载荷与收件人 |
| POST | `/admin/notifications/dead-letters/{eventId}/replay` | SYSTEM_ADMIN；非空 reason、幂等键；有界检索最多 100 条 |

候补成功登记 HTTP 201，version=0；动作成功 HTTP 200 并增加版本。详情含固定资源、同组位置、当前截止、关联 applicationId 和 allowedActions。技术防滥用上限是每人 50 条有效候补，不作为学校制度参数。关键错误：DUPLICATE_WAITLIST、WAITLIST_NOT_NEEDED、WAITLIST_PRIORITY、VERSION_CONFLICT、OFFER_EXPIRED 为 409；APPLICATION_LIMIT_REACHED、COVERAGE_UNKNOWN、RESOURCE_CLOSED、WAITLIST_LIMIT_REACHED 等为 422。

Web 新增“我的候补”“站内通知”和仅系统管理员可见的“消息投递管理”。候补可选择固定组合登记、查看当前状态、确认转为申请、取消；成功转换提供关联申请入口。可用组合提交遭遇占用或队列优先冲突后，可按原条件登记候补。日历增加 WAITLIST_HOLD 类型，只公开时段和类型，不公开本人信息。所有时间输入和展示使用上海时区。

通知显示事件历史。打开关联记录时重新读取当前申请或候补，晚到的“已批准”等通知不会将当前已取消对象恢复批准。通知页面在可见时每 20 秒刷新，服务端仍决定实际状态。

## 3. 消息可靠性

预约和候补状态、占用、审计及 Outbox 同一 MySQL 事务提交。发布器使用短事务认领、事务外发送、发布确认后按 claim_token 更新，支持过期 SENDING 租约恢复。多个实例通过 FOR UPDATE SKIP LOCKED 认领；旧实例晚到的结果不能覆盖新租约。

消息包含 eventId、eventType、aggregateType、aggregateId、aggregateVersion、occurredAt、recipientIds、最小 payload、traceId 和 deliveryScope，不携带用户访问令牌、密码、密钥或导入文件。队列和交换器按 JWT audience 的 SHA-256 派生名称，dev/prod 及独立验收 scope 分离。发布器只领取本 scope 的事件，通知收件箱也按 scope 隔离。

使用持久 direct exchange、持久消息和 quorum queue；mandatory 返回消息或负发布确认不能标记 SENT。通知队列采用 quorum 的 at-least-once 死信策略和 reject-publish 溢出策略，死信目标也是持久 quorum queue。发布确认、消费提交与用户已读是三个不同阶段，SENT 仅代表发布确认。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)、[死信与可靠性约束](https://www.rabbitmq.com/docs/dlx)。

默认最多 5 次主投递、30 秒认领租约、3 秒发布确认，指数退避最多 60 秒；连接 2 秒、通道 RPC 3 秒、心跳 10 秒。通道 RPC 超时覆盖建立通道和协议交互，不能只依赖发布确认计时。主投递耗尽进入 FAILED；尝试将原消息放入死信。broker 仍不可用时，失败事件继续保留在 MySQL，以有界间隔补偿死信投递，不丢弃。配置由 OUTBOX_MAX_ATTEMPTS、OUTBOX_LEASE_SECONDS、OUTBOX_CONFIRM_TIMEOUT_MS、OUTBOX_RETRY_BASE_MS 等控制。

通知服务使用独立 notification_db 与分库账号。consumed_event 去重锁、所有收件人的 notification、站内 delivery_attempt 和 processed_at 同事务提交，提交后才手工 ACK。相同 eventId、相同载荷的重投不重复写；相同 eventId 的不同载荷拒绝消费。消息超过 64 KiB、契约错误或消费数据库失败经过最多三次有界尝试后进入死信。消费提交后 ACK 丢失可重投，由已提交去重记录恢复。

人工 Outbox 重试保留 eventId，复用原幂等键返回原结果。死信重放先确认新发布，再记录成功并 ACK 原死信；跨 MySQL/RabbitMQ 不提供分布式原子事务，可能重复发送，但不会重复通知。非法载荷不能直接重放。死信预览和检索有数量限制，并不保证死信顺序。

历史 M3 事件迁移为 delivery_scope=legacy，默认不自动投递。升级时先备份、核对旧事件，再由维护者显式设置 BOOKING_ADOPT_LEGACY_EVENTS=true 进行一次接管并关闭该选项；不要把旧 PENDING 记录当作用户已经收到消息。本次验收不开启历史事件接管。

## 4. 缓存与后台身份

Redis 仅缓存已提交的目录展示字段，默认 TTL 60 秒，上限 300 秒，键按 scope 隔离。先读取 MySQL 当前目录和权限，再核对缓存资源版本；写事务和一致性事务不发布或读取缓存值，资源提交后失效。腐坏、旧版本或 Redis 不可用时回源。来源覆盖、开放判断、占用、配额及审批资格均不作为缓存真值。

后台只读资格接口 `/internal/booking/applicants/{id}` 仅通过身份服务内部地址访问，网关没有对外路由。独立 32 字节 HMAC 密钥只交给 booking/identity，签名绑定部署 audience、GET 路径、10 秒时间窗口和 UUID nonce；Redis 保证 nonce 一次性。返回 userId/status/roles，不赋予用户创建、角色变更或会话访问权。普通用户 JWT 无法替代服务签名，身份或防重放设施不可用时保持待评估，不误判用户失去资格。

## 5. 环境、迁移与运行

首次配置或已有 M3 环境升级，在基础 `.env` 和 init-auth 完成后执行：

```sh
python3 deployment/scripts/prepare-messaging.py dev
python3 deployment/scripts/prepare-messaging.py prod
python3 deployment/scripts/bootstrap-nacos.py dev
python3 deployment/scripts/prepare-idea.py
./GraduationProject/mvnw -s .mvn/settings.xml -B -ntp verify
```

prepare-messaging 留存各环境独立 booking-service-call.key、login-peer.key 与 notification.env，不重置已有账号密码，文件权限 600 且 Git 忽略；prod 只准备文件，不启动。后台资格密钥仅交给 booking/identity，登录来源密钥仅交给 gateway/identity。notification.env 使用已经建立的本环境通知分库账号和 RabbitMQ 凭据。IDEA“后端总启动（dev）”现在包含 identity 8083、booking 8082、notification 8085、gateway 8081；Web 仍为 5173。命令行 dev-workspace.py 同样启动四个 Java 服务和 Web。独立启动通知：

```sh
python3 deployment/scripts/run-service.py dev notification-service
```

预约库新增 V4：waitlist_group、成员、waitlist_entry、占用 owner XOR 约束、两类 owner 的复合外键及 Outbox 投递字段。通知库 V1：消费去重、通知、渠道投递历史、人工重放租约。V4 和通知 V1 已在本机 dev 执行，**不得编辑，包括排版**；后续必须新增迁移。执行前已将两个库备份至被忽略的 secrets/dev/backups/before-waitlists-messages-20261013-*.sql，权限 600。非空环境采用前向修复，恢复需隔离数据库演练并核对状态、占用、事件；本阶段没有宣称完成灾备演练。
