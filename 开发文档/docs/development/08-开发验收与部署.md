# 开发验收与部署

## 1. 开发阶段

| 阶段 | 产物 | 验收门槛 |
| --- | --- | --- |
| M0 需求确认 | 规则确认表、真实/演示数据边界、角色与流程 | 关键问题有明确答案或演示假设 |
| M1 技术验证 | 最小服务与 App 构建验证、版本锁定表 | Nacos/Gateway/Feign/SQL/AI 能调用；双平台基础运行 |
| M2 目录与身份 | 数据库迁移、导入、登录、授权、Web 基础页 | 导入统计正确，来源完整，权限有效 |
| M3 预约核心 | 申请、审批、取消、暂占、幂等 | 一处场地与设备整体提交、竞争无重复占用 |
| M4 候补与消息 | 候补、Outbox、通知、超时、Redis | 重启、重投、超时与竞争均可恢复 |
| M5 AI | 多轮条件、只读工具、方案、降级 | 不猜缺失关键条件，不绕过业务权限与提交检查 |
| M6 多端 | Web 管理与两平台学生流程 | iOS/Android 分别安装运行并留存记录 |
| M7 集成部署 | Compose、Nginx、日志、备份、测试记录 | 按文档可部署和恢复，关键用例真实执行 |

按里程碑推进，不强行给未核实工作量指定固定周数。初试前优先需求确认与最小验证，编码时间与个人备考安排协调。每个阶段产物进入版本管理。

## 2. 关键测试清单

以下是完整验收清单。M3 预约核心与此前身份、目录的已执行结果见 [联合预约验收](19-M3联合预约闭环.md)，其余候补、投递、AI、多端与上线场景仍待相应阶段实现和验证，不将设计期望当作通过记录。

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| T-01 | 同一资源区间并发创建申请 | 最多一笔有效占用，其他冲突；数据库记录无部分申请 |
| T-02 | 联合申请里设备冲突 | 所有资源和申请整体回滚 |
| T-03 | 相接与部分重叠区间 | 按半开区间判断正确 |
| T-04 | 同键同请求重投 | 同状态码同申请；Outbox 不重复产生 |
| T-05 | 同键不同内容 | IDEMPOTENCY_KEY_REUSED |
| T-06 | 不同资源同时触发用户配额 | 不超过上限，guard 锁有效 |
| T-07 | 审批与取消/过期竞争 | 只产生一个合法状态转换，释放完整 |
| T-08 | 多管理员审批 | 首个有效动作生效，其余冲突 |
| T-09 | 定时器延迟 | 过期 HOLD 不继续阻塞可用性，查询/提交正确识别 |
| T-10 | 候补提升与直接申请竞争 | 同组策略正确，无重复暂占 |
| T-11 | 候补确认与超时竞争 | 只有申请转换或过期一种结果 |
| T-12 | 候补确认时配额变化 | 正确核验；确认不重复计数自己的 offer |
| T-13 | 来源覆盖不完整/失效 | UNKNOWN，真实模式下不自动申请 |
| T-14 | 外部占用更新与申请竞争 | 同锁协议；已批准冲突进入审查，不隐瞒 |
| T-15 | 外部冲突重新验证 | 仍有冲突时不恢复批准；解除后符合条件才恢复 |
| T-16 | 导入重复、缺字段、空容量 | 预览可定位；不误删、不把空当零 |
| T-17 | 管理员跨组与学生查看他人申请 | 服务端拒绝，不泄露私有资料 |
| T-18 | JWT 过期/错误受众/会话撤销 | 服务端拒绝，客户端刷新或登录 |
| T-19 | RabbitMQ 不可用 | 业务 Outbox 持久化；恢复后发送 |
| T-20 | 投递后确认丢失 | 允许重发，通知去重有效 |
| T-21 | 消费提交后 ACK 丢失 | 重投无重复通知 |
| T-22 | Outbox 认领后进程退出 | 租约到期恢复，不永久卡在 SENDING |
| T-23 | 消息乱序 | 保留历史，界面当前状态不回退 |
| T-24 | Redis 失效或缓存过期 | 预约仍由真实数据库判断，不产生超额 |
| T-25 | AI 缺时间、多轮变更、无效资源 | 追问/校验，保留未变条件，不虚构资源 |
| T-26 | AI 查后资源被占用 | 提交返回冲突而非沿用旧结果 |
| T-27 | AI 请求越权、格式错误、超时 | 权限拒绝或明确失败，普通筛选可用 |
| T-28 | iOS/Android 网络中断与重复点击 | 重试原键，依据服务端恢复状态 |
| T-29 | App 前后台切换、过期候补 | 刷新真实状态，倒计时不决定业务结果 |
| T-30 | 备份与恢复 | 恢复后申请、占用和消息一致性可检查 |

并发测试使用真实 MySQL/InnoDB，消息测试使用真实 RabbitMQ；Testcontainers 需要 Docker 正常运行。实现先验证事务与约束，再做 JMeter 负载测试。测试样例与真实学校数据分别标记。

## 3. 指标定义

记录目录规模、开放资源数、申请数、并发数、机器配置、依赖版本、p50/p95 响应时间、成功/冲突/错误数、死锁和重试次数。冲突是正常业务结果，应与系统错误分开统计。

AI 记录人工期望条件、抽取正确字段、错误/遗漏、工具调用是否正确、最终方案有效性、耗时和调用量。不先填目标达成值，不把模型自评分当真实准确性。

业务统计第一版提供申请与状态数量；如加入利用率，须先定义完整开放时间分母、来源覆盖范围和重叠区间去重方法。

## 5. 部署拓扑与配置

演示环境采用 Docker Compose：MySQL、Redis、RabbitMQ、Nacos、Gateway、四个业务服务、Nginx/Web。App 连接网关 HTTPS 地址。MySQL 可共实例分四库，服务使用分库账号。设备访问与服务器网络在 M1 验证。导入原文件保存到受控持久卷，按服务生成的存储键访问；多实例需共享受控存储，保存文件 hash 与批次对应关系。

配置清单：数据库 DSN 与凭据、Redis、RabbitMQ、Nacos 地址/命名空间、JWT 私钥/JWK/iss/aud、模型服务地址/密钥/预算、业务时区、规则键、日志与备份目录。公开示例文件只放占位值，真实配置通过环境变量或私有配置管理。

MySQL/Redis/RabbitMQ 管理端口、Nacos 控制台和 Actuator 仅允许受控访问；业务流量通过网关。为 Web 配置 HTTPS 和跨域/同源策略，网关信任转发头仅来自受控 Nginx。

## 6. 启动与验证顺序

1. 锁定组件与镜像版本，准备配置和持久化目录。
2. 启动 MySQL、Redis、RabbitMQ、Nacos，分别确认健康。
3. 按库执行经过验证的 Flyway 迁移，检查账号权限。
4. 启动 identity、booking、notification、AI，检查依赖就绪与 Nacos 注册。
5. 启动 gateway，验证认证、路由、Feign 和 traceId。
6. 启动 Nginx/Web；配置 App API 地址并验证两平台。
7. 导入有来源标记的资源与占用，执行联合预约、审批、取消、候补、AI 主流程。
8. 执行消息恢复、重复请求与备份恢复抽检，保存结果。

启动检查不只看进程存活；API 能返回不代表锁、权限和消息恢复已经正确。完整验收需执行对应 T-xx。

## 7. 备份与故障处理

迁移和重要导入前备份四库，保存与备份对应的版本和配置。备份不包含未保护的模型/JWT 密钥。恢复演练在隔离环境执行，核对申请、占用、Outbox、消费记录和通知，允许重投但不能重复写业务。

关键排查顺序：traceId → 服务日志 → 申请版本与占用 → Outbox 状态/租约 → RabbitMQ 队列 → 通知去重与投递。数据库死锁记录与重试上限单独观察，不能无限重试。
