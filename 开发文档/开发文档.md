## 已确认的项目目标

校园活动一次性申请场地和设备；支持管理员审批、时间冲突检查、取消、候补和通知。通过 Spring AI 理解自然语言查询。最终覆盖 Web 管理端与 iOS/Android 学生端，使用 Java 微服务、MySQL、Redis 和 RabbitMQ。

老师在聊天中表示方向可以继续，并愿意协助联系数据。学校实际借用范围、审批人和占用数据完整性尚未确认；本文件中的具体工作流属于开发建议。

## 主要设计决策

| 编号 | 决策 | 原因与影响 |
| --- | --- | --- |
| D-01 | 场地、单件设备、预约、审批、候补共属预约服务 | 联合预约与资源释放在一个 MySQL 本地事务内完成 |
| D-02 | 所有占用写入口先按 ID 升序锁定资源行 | 即使当前无占用记录，也有稳定的并发保护对象 |
| D-03 | MySQL 保存占用和有效期；Redis 缓存目录 | 缓存延迟不会成为预约成功的判据 |
| D-04 | Outbox 与业务同事务，RabbitMQ 异步通知 | 预约提交与事件之间可恢复；接受重复投递并去重 |
| D-05 | AI 只请求受控的只读工具 | 身份、容量、时间和最终写入由业务接口检查 |
| D-06 | 多端共用契约，预约提交携带幂等键 | 网络重试、重复点击不会产生重复写入 |
| D-07 | 外部占用有覆盖范围与来源状态 | 未知数据不能直接转换为“空闲” |
| D-08 | 待审批暂占、候补暂占有明确有效期 | 过期可恢复；期限值由业务负责人确认 |
| D-09 | 同一申请由统一审批组处理 | 第一版仅开放可统一审批的资源组合 |

## 实现前优先确认

1. 一期允许预约哪些场地和设备，谁负责审批？
2. 导出的空闲结果是否包含查询日期、节次和完整覆盖范围？是否还有临时借用与考试安排？
3. 待审批是否暂占、审批期限、活动开始前最晚提交时间？
4. 已批准申请能否取消、取消截止时间、候补确认期限？
5. 同一候补组的排序规则，以及不同组合间的公平性要求？
6. 双端采用真机还是模拟器演示？是否要求关闭 App 后仍收到系统推送？

这些答案形成需求版本。业务不确定时可以使用明确标识的演示规则完成设计讨论，不能把演示规则描述成学校已实行制度。
