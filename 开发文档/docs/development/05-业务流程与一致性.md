# 业务流程与一致性

2026-10-13：联合预约与来源冲突状态机已实现并通过真实 dev MySQL 验证，详见 [闭环说明](19-M3联合预约闭环.md)。下文候补与消息投递部分仍是 M4 设计。

## 1. 状态及资源效果

| 申请状态 | 允许来源 | 资源占用 | 允许的主要动作 |
| --- | --- | --- | --- |
| PENDING_APPROVAL | 创建申请或候补确认 | HOLD，有效期 | 批准、拒绝、本人取消、过期 |
| APPROVED | 合法审批 | CONFIRMED，至活动结束 | 按规则取消、完成、外部冲突审查 |
| CONFLICT_REVIEW | 新学校占用/关闭规则与已批准申请冲突 | 保留原占用并标记冲突 | 管理员取消或重新验证恢复批准 |
| COMPLETED | 活动结束且处于 APPROVED | RELEASED | 只读 |
| REJECTED | 拒绝待审批 | RELEASED | 只读 |
| EXPIRED | 待审批到期 | RELEASED | 只读 |
| CANCELLED | 合法取消/冲突处置取消 | RELEASED | 只读 |

CONFLICT_REVIEW 不自动变成 COMPLETED 或重新批准；需要管理员处置。它保留申请资源，避免外部数据到达时悄悄丢失其他已配套资源。不能宣称这个冲突申请仍可正常使用。

| 候补状态 | 资源效果 | 后续 |
| --- | --- | --- |
| WAITING | 无占用 | 评估为 OFFERED，或用户取消、过期 |
| OFFERED | 全部资源 HOLD | 用户确认、取消、超时 |
| CONFIRMED | 占用转交新申请 | 通过 applicationId 查看审批 |
| EXPIRED / CANCELLED | 释放所属 HOLD | 终态 |

完整候补申请内容创建后固定。需求改变要取消后重新申请，不修改已参与排队的资源集合和时段。

## 2. 创建申请事务

```text
校验身份与基本参数
  → 在本服务事务中声明幂等键
  → 锁固定 booking_write_guard，稳定关联申请及成员集合
  → 锁用户配额（预约库中的幂等/配额稳定对象，见下文）
  → 按资源 ID 升序逐个 SELECT ... FOR UPDATE 锁资源主键行
  → 校验角色、审批组、数据模式、容量、开放、来源覆盖
  → 当前读取检查外部占用和有效平台占用
  → 检查同组合候补优先规则（M4 接入，当前没有候补入口）
  → 创建申请与全部占用、审计、Outbox，保存幂等结果
  → COMMIT，返回 201
```

所有资源必须存在且锁定数量与请求一致。逐个主键升序锁定用于统一锁顺序，不能假定复杂 IN/ORDER BY 查询一定按预期顺序加锁。

预约事务明确使用 READ COMMITTED，取得协调行与资源行锁后，在 READ COMMITTED 中读取最新已提交的冲突记录，避免使用此前快照或缓存。若实际实现改用 REPEATABLE READ，必须重新验证当前读取与快照区别。重叠条件：existing.start_at < requested.end_at AND existing.end_at > requested.start_at。HOLD 只有 expires_at 大于数据库当前时间才有效；CONFIRMED 受区间约束。

用户申请额度和同人重复申请也需要稳定锁定对象。预约库增加 `applicant_guard(user_id BIGINT PK,created_at,updated_at)`；增加配额的写申请和候补提升先按用户 ID 锁 guard，再锁资源。guard 初次使用幂等创建。确认 OFFERED 转申请时排除自己的 offer，整体计数不增加。guard 锁后在 READ COMMITTED 下读取最新配额，所有增加计数的入口均串行；减少计数的入口可并发，至多造成暂时保守拒绝，不会超过上限。

当前整体锁顺序：请求幂等记录（若有）→ booking_write_guard → applicant_guard（增加配额或确认 offer 时）→ resource（升序）→ waitlist_group → 所属 application/waitlist。多用户增额任务按用户 ID 升序锁 guard；后台任务必须遵循相同顺序，不在持有申请行锁后反向获取资源。资源成员关系固定，因此先读取成员 ID，再按顺序加锁后重新核验 owner 状态是安全的。来源和目录修改先扩展关联有效申请的全部成员，再一次按资源 ID 升序锁定；首版固定协调行将业务写入串行化，吞吐优化与容量验证后续进行。

唯一幂等键冲突可能等待另一事务提交；提交后返回持久化的原结果。不能把唯一键异常捕获后继续使用已失败事务。等待超时返回 REQUEST_IN_PROGRESS；重试复用原键。键的 actor/operation/hash 一起核对。

## 3. 审批、拒绝、取消和超时

读取不可变资源成员 → 获取需要的 guard/资源锁 → 锁申请行 → 核对 expectedVersion 和当前状态 → 检查权限与截止时间 → 原子更新状态和所有占用 → 写审批/审计/事件 → 提交。

批准要求暂占仍有效，学校占用、开放与资格仍满足；转为 CONFIRMED 并清空有效期。失败不能把部分资源改为 CONFIRMED。

拒绝、取消、过期将全部所属占用转 RELEASED。处理重复状态时返回既有结果或 INVALID_STATE；不得重复生成不同版本的释放事件。

时间任务先查询候选 ID，然后按协议逐笔处理，禁止扫描时先批量锁申请再获取资源。任务重启可以重复扫描；状态条件更新和 version 保证只转一次。业务请求遇到过期 HOLD 时也执行到期校验，避免定时器延迟阻塞真实空闲资源。

## 4. 候补排队与提升

组定义：完全相同的排序资源 ID、固定 UTC 时段和 data_mode。组内按 created_at,id 排序；不同资源组合之间只保证不冲突，不保证全局 FIFO。

创建候补先锁对应资源和 group 行，确认有冲突且没有同用户的有效候补后入队。资源已全部可用则返回 WAITLIST_NOT_NEEDED。创建候补不占资源。

提升步骤：按统一顺序获取 guard/全部资源/group/候选 entry 锁，重新读取队首与状态；检查资源、来源覆盖、申请资格和最晚提前量；符合条件时为全部资源写 HOLD，entry 转 OFFERED 并生成通知。

队首因停用、提前量等永久不满足条件时标 EXPIRED 并说明原因；暂时冲突时保持 WAITING。候补有效的同组请求优先于新直接申请，直接申请锁定资源后检查 group 的 WAITING/OFFERED 状态，必要时返回 WAITLIST_PRIORITY。

确认在一个事务中创建 PENDING_APPROVAL 申请，转移整组占用 owner，重新计算审批暂占期限，entry 转 CONFIRMED。确认仍需资格和配额检查。offer 到期与确认同时竞争只允许一个合法结果。

释放事件触发候补评估；周期补偿扫描恢复丢失触发。评估/通知动作可重复，但相同资源不能重复暂占。

## 5. 外部占用与开放变化

目录导入不改变占用。学校占用导入使用明确覆盖范围和导入批次，并按照资源 ID 升序锁定相关资源后原子更新。若为完全覆盖替换，只替换该来源、资源、时间范围内的记录；跨范围不删除。

新占用与 PENDING_APPROVAL 冲突时将申请 REJECTED，记录 SOURCE_CONFLICT，释放全部资源；与 OFFERED 冲突时使候补 offer EXPIRED 并释放；与 APPROVED 冲突时转 CONFLICT_REVIEW，保留原配套占用并通知双方。尚在 WAITING 的候补仍按可用性重评。

管理员 CANCEL 冲突申请时整体释放；REVALIDATE 时获取全部资源锁，重新核实来源覆盖、开放和外部占用，排除本申请自己的占用后检查其他占用，满足才恢复 APPROVED。历史来源冲突记录和处置审计不能删除。

来源范围不完整时记 PARTIAL，不将缺失记录认定空闲。一次导入失败事务回滚，不能更新半份覆盖并展示为 COMPLETE。

## 6. Outbox 与通知

Outbox 随状态变更同事务写入。投递程序短事务认领 PENDING 或租约已到期的记录，记录 claim_token 和 claim_expires_at；发送后使用发布确认更新 SENT。claim 过期允许恢复。发送成功但确认丢失可以重投。

消费者先检查/插入 consumed_event 唯一键，再同事务写入通知。事务提交后 ACK；重复 eventId 无重复通知，可直接 ACK。不同事件到达乱序时保留历史，但不能把对象当前状态回退；点击通知由前端重新获取详情。

有限重试后送死信队列，记录原因并提供人工检查与重试流程。消息持久化、持久队列、发布确认与消费确认分别配置。官方机制参考 [RabbitMQ 确认文档](https://www.rabbitmq.com/docs/confirms)。

Redis 目录缓存有 TTL 和更新失效机制，事务提交后刷新/失效；失败靠 TTL 修复。占用查询与写入直接检查 MySQL。学校来源同步状态不从 Redis 推断。

## 7. 失败与恢复

| 失败点 | 预期处理 |
| --- | --- |
| 写入一个资源后异常 | 申请、全部占用、审计、Outbox 一并回滚 |
| 响应丢失但提交成功 | 客户端原键重试或查本人记录，返回既有申请 |
| 审批与取消竞争 | 相同资源锁和状态版本；只有一个状态变化有效 |
| 进程在 Outbox 认领后退出 | 租约到期重新认领，事件 ID 不变 |
| 消费通知提交后 ACK 丢失 | 重投由 consumed_event 去重 |
| Redis 不可用 | 限流按明确降级策略；最终预约照常校验数据库 |
| 模型不可用 | 返回 AI_UNAVAILABLE，普通筛选仍可使用 |
| 外部覆盖失效 | UNKNOWN；不返回未经确认的 AVAILABLE |

联合申请、配额、审批/取消竞争、来源冲突及多实例到期补偿已在真实 MySQL 验证。候补与消息投递尚未实现，死锁重试策略、容量和 RabbitMQ 故障恢复仍需后续验证。MySQL 锁语义参考 [官方文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。
