# 校园资源预约：技术栈与开发流程

版本：方案 v1.0 · 2026-10-08

详细需求、数据库、API、页面与异常流程已整理到 [开发文档](开发文档.md)。本文件保留前期选型概览；字段与细节以开发文档为准。

本文件是开发方案与阶段验收清单。服务和依赖尚未搭建，版本兼容性依据官方文档核对，实际构建与运行将在第一阶段验证。

## 1. 项目目标与当前边界

学生为一次活动联合申请场地与设备，管理员审批，系统处理占用冲突、取消释放、候补与消息。AI 将自然语言需求转成查询条件并调用业务接口。Web 管理端、iOS 和 Android 学生端共用后端。

老师已在聊天中表示该方向可以继续，并愿意协助联系数据；具体业务规则仍需确认。学校场地目录可以通过 Excel/JSON 导入，正式运行范围取决于获得的占用数据、借用规则和管理方配合。

已读取的样本：Excel 含 3 条记录、17 列，三条“是否可借用”均为“是”；JSON 报告总数 1,132，本页实际 100 条，`sfkjy` 均为“否”。数据来自不同导出范围，不能直接将所有目录记录设为可预约。JSON 中的日期不能单独证明某日某节次空闲，需结合原查询条件确认。

真实数据和开发演示数据保存来源标记。模拟安排用于原型开发和功能测试；测试结果来自实际执行，学校实际使用效果需另行记录。第一期把场地范围限定为管理方确认的一批资源。

| Web | Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router | 资源导入、日历、审批、候补与统计 |
| iOS / Android | uni-app（Vue 3）、TypeScript、uni-ui、HBuilderX | 资源查询、活动申请、预约记录、通知、AI 对话 |
| 后端 | Java 21、Spring Boot、Maven Wrapper | 业务 API、校验、事务、应用配置 |
| 网关 | Spring Cloud Gateway | 路由、统一入口、身份检查、限流 |
| 服务发现与配置 | Spring Cloud Alibaba Nacos 适配器、Nacos Server | 注册发现、按环境管理配置 |
| 服务调用 | Spring Cloud OpenFeign、LoadBalancer | AI 等服务调用预约服务 |
| 身份权限 | Spring Security、JWT、BCrypt、RBAC | 用户登录、签名校验、角色与管理范围校验 |
| 持久化 | MyBatis-Plus、MySQL InnoDB、Flyway | 数据访问、SQL、事务、索引、数据库迁移 |
| 缓存 | Redis | 资源目录缓存、限流、会话撤销信息；预约有效性由 MySQL 决定 |

| 定时任务 | Spring Scheduling | 暂占超时、候补超时、Outbox 投递、消息补偿 |
| AI | Spring AI、支持工具调用的大模型服务 | 多轮条件提取、参数校验、查询工具调用、结果解释 |
| 数据导入 | Apache POI、JSON 解析、Jakarta Validation | Excel/JSON 预览、校验、映射、批量导入 |

Web 与 App 分开开发页面，复用接口契约和业务概念。Element Plus 用于 Web；移动端采用 uni-app 组件并分别进行 iOS/Android 适配。模型密钥保存在服务端。移动端采用安全存储保存会话凭据，传输使用 HTTPS。

App 第一版实现站内消息和主动刷新，后续可增加在线消息通道。App 关闭时的系统推送需要额外接入推送服务并配置两个平台，作为单独验收项。iOS 的签名、安装方式与可用设备在第一阶段验证。

## 3. 服务边界

| 服务 / 模块 | 职责 | 数据所有权 |
| --- | --- | --- |
| `gateway` | 外部 API 入口、路由、身份检查、请求标识、限流 | 不存业务数据 |
| `identity-service` | 本地账号、登录、角色、账号状态、设备会话 | `identity_db` |
| `booking-service` | 场地与设备、导入、外部占用、申请、审批、候补、规则和审计 | `booking_db` |
| `ai-service` | 对话、结构化条件、只读查询工具、调用记录 | `ai_db` |
| `notification-service` | 站内消息、通知投递、重试与消费去重 | `notification_db` |

一个 MySQL 实例中建立不同逻辑库，各服务通过 API 或事件交换数据，使用独立数据库账号。场地、设备和预约共属预约服务，一次联合预约只访问 `booking_db`，在本地事务内提交。业务服务还要验证身份及管理范围，不能仅依赖网关检查。

初期先跑通 identity、booking 与 Web 的最小流程，随后增加独立 AI、通知服务。最终交付包含上表全部服务。架构图见 [系统边界](docs/architecture/c4-context.md) 和 [服务与数据关系](docs/architecture/c4-containers.md)。

## 4. 核心业务规则草案

以下为实现建议，定稿前与老师或资源负责人确认。

- 角色：学生、资源管理员、系统管理员；资源管理员只操作其负责范围。
- 时间统一按 `Asia/Shanghai` 解释，数据库按确定的统一时间约定存储。预约区间采用 `[开始, 结束)`，相接时段允许连续使用。
- 设备第一版按实际单件登记，例如两支麦克风对应两个设备资源 ID；联合申请显式选择所需资源。
- 场地的来源借用标记、平台开放规则、外部占用分别保存。平台管理员确认开放范围后才能接受申请。
- 候选流程：提交后暂占全部资源并待审批；暂占期限可配置。拒绝、取消或超时释放全部资源。审批时重新检查期限和外部占用。
- 第一版一次申请由一位具有整组资源审批权限的负责人审批；无法统一管理的组合不开放联合申请。多部门会签后续再讨论。
- 候补第一版针对确定的资源组合与时间区间排队。进入候补不占资源；轮到用户时原子地暂占全部资源，等待确认；确认后进入审批。候补确认期限可配置。
- 同一候补组内按申请时间和 ID 排序。不同资源组合之间不承诺全局先到先得，实际策略需在需求文档中明确。

申请主要状态：`PENDING_APPROVAL` → `APPROVED` → `COMPLETED`；待审批可进入 `REJECTED` / `EXPIRED` / `CANCELLED`，已批准可按规则取消。资源占用另存状态与有效期，状态转换和资源释放在同一事务中完成。

候补状态：`WAITING` → `OFFERED` → `CONFIRMED`；通知后可超时，用户可取消。确认将候补关联到一笔预约申请。每次操作都检查当前状态，避免重复确认与重复释放。

## 5. 数据模型的起点

| 归属 | 主要表 | 用途 |
| --- | --- | --- |
| identity | `user`、`role`、`user_role`、`user_session` | 账号、权限、设备会话 |
| booking | `resource`、`equipment_detail`、`resource_manager` | 场地设备、属性与管理权限 |
| booking | `resource_opening_rule`、`external_occupancy` | 开放规则、学校已占用安排及来源 |
| booking | `activity_application`、`application_resource` | 活动需求、联合申请资源 |
| booking | `resource_occupancy`、`approval_record` | 实际占用、有效期、审批历史 |
| booking | `waitlist_entry`、`waitlist_resource` | 候补组合、区间、确认期限 |
| booking | `import_batch`、`import_error` | 导入来源、覆盖范围、错误和统计 |
| booking | `idempotency_record`、`outbox_event`、`audit_log` | 重复请求、可靠事件、操作审计 |
| notification | `notification`、`consumed_event` | 用户消息、消费去重 |
| ai | `conversation`、`message`、`tool_call_record` | 对话、结构化条件、查询依据与调用结果 |

来源系统 ID 按字符串保存，使用“来源系统 + 来源 ID”唯一约束；数量字段将数字字符串校验后转换，空值保持未知。`jgmc` 等字段的业务含义需核对，不能直接等同管理员或托管部门。

导入先预览与校验再提交，保留原始来源及批次。默认按来源 ID 更新基础属性；单次导出里未出现的资源不自动删除。导入基础目录不覆盖平台内预约。外部占用导入需明确完整覆盖范围；不能把缺失记录直接认定为空闲。

## 6. 四条技术主线

### 联合预约与并发

同一事务中按资源 ID 升序锁定所有涉及的资源记录，检查开放规则、有效外部占用和平台占用，再写入整笔申请、全部占用及 Outbox 事件。任一条件不满足，整体回滚。

使用资源记录作为稳定锁定对象，避免只锁“查询到的占用记录”却在无记录时失去保护。重叠判断为 `existing.start < requested.end` 且 `existing.end > requested.start`。所有改变占用的写入口（申请、审批、取消、候补暂占、关闭时段、外部占用更新）遵循相同锁定协议。

状态写入采用条件更新/版本检查，过期任务与用户操作竞争时只允许一次转换。重复请求使用“用户 + 操作 + 请求 ID”唯一记录；请求内容不同却使用同一 ID 时返回冲突。同一用户从不同端发起语义相同申请仍需业务校验，不能仅依赖按钮禁用。

### 消息与定时恢复

业务事务同时写 Outbox。定时投递程序发布到 RabbitMQ，收到发布确认后标记已发送；确认不明时允许重发。消费者以事件 ID 去重，将通知与消费记录在同一事务写入，再确认消费。

采用有限重试和死信队列，保留人工重试入口。同一预约事件包含状态版本，通知消费处理重复与乱序。消息正文不包含无关个人信息。

暂占与候补有效期保存在 MySQL。定时任务批量扫描，使用条件更新和统一资源锁确保多个实例不会重复处理。查询和提交同时识别已过期占用，避免单纯等待定时器。资源释放后触发候补评估，同时保留周期补偿扫描以恢复遗漏工作。

### AI 与真实业务接口

流程：自然语言 → 结构化条件 → 参数校验/追问 → 只读工具查询 → 方案卡片 → 用户确认 → 预约服务提交。

结构包含绝对起止时间、人数、校区、设备类型及数量、地点偏好。相对时间依据服务端当前时间和时区解析，并将绝对日期展示给用户确认。

AI 工具只开放 `searchAvailableResources`、`getResourceDetails`、`getBookingRules` 等必要查询方法。工具请求携带可信用户身份，预约服务执行权限和范围校验。模型输出的资源 ID、时间、容量都再次校验；最终申请走普通业务接口。上下文中的历史方案可能过期，提交时重新检查。模型不可用时保留表单与条件筛选入口。

先做工具调用和多轮条件管理。若规则文档足够，再讨论规则问答与 RAG；空闲状态始终由业务查询提供。

### 多端与权限

Web 与 App 共享 API 契约、错误码及分页格式。App 处理令牌刷新、网络失败、请求幂等和状态重新获取；预约成功以服务器响应为准。

系统管理员、资源管理员、学生的操作权限及数据范围逐项测试。每个服务验证 JWT 的签名、有效期、发行者与受众，再检查账号状态及业务权限。资源查询工具不能改变调用者身份。

iOS / Android 分别验收登录、查询、提交、取消、候补确认、消息与 AI 多轮查询。扫码核销、系统离线推送等附加能力单独确认范围。

## 7. 开发流程与阶段验收

| 阶段 | 工作 | 完成标志 |
| --- | --- | --- |
| 0：需求与数据 | 确认资源范围、审批人、暂占期限、候补规则、数据获取；梳理角色与用例 | 需求清单获老师确认；字段来源与未知项明确 |
| 1：技术验证 | 创建最小工程；验证版本组合、MySQL、Nacos、Gateway、Feign、AI 工具调用；App 两平台基础运行 | 形成版本锁定表；所有组件最小集成通过；确认 iOS 安装/演示方式 |
| 2：业务基础 | 数据库迁移、登录权限、资源导入、目录、开放与占用维护、Web 基础页 | 可导入样本；不同角色访问范围正确；所有来源有记录 |
| 3：预约核心 | 实现联合申请、暂占、审批、拒绝、取消、幂等和审计 | 同资源并发最多一笔有效重叠占用；任一资源冲突时整笔回滚 |
| 4：候补与通知 | 独立通知服务、Outbox、RabbitMQ、重试、死信、候补与过期任务、Redis 缓存及限流 | 重启恢复；重复消息不重复通知；候补整组暂占与超时释放正确 |
| 5：AI 查询 | 接入 Spring AI、多轮条件、查询工具、方案卡片、用户确认 | 复杂需求能被核查；权限不越界；旧方案提交重新校验；失败可转表单 |
| 6：双端 App | uni-app 学生端；认证、预约、候补、通知、AI；平台适配 | iOS 和 Android 分别完成全部主要流程并保存演示记录 |
| 7：集成与部署 | Compose/Nginx、健康检查、统一日志、并发与故障测试、数据备份恢复 | 可按说明部署；测试记录说明环境、步骤、结果与局限 |
| 8：总结材料 | 需求、架构、数据库、接口、关键实现、实际测试和演示整理 | 原始测试记录可追踪；独立撰写论文；按学校要求披露 AI 使用 |

各阶段按依赖顺序交付，允许界面设计与已稳定接口的前端开发并行。初试前优先完成需求确认和技术验证；较大规模编码结合备考时间安排，复试前争取有完整核心流程。学校开题和中期节点以正式通知及学院要求为准。

每个功能采用：确认用例 → 状态/数据约束 → API 契约 → 后端实现 → 前端联调 → 关键验证 → Git 提交 → 记录问题与取舍。API 标注认证方式、幂等请求 ID、时区、状态变化及错误含义。

## 8. 必须验证的场景

| 场景 | 验收依据 |
| --- | --- |
| 多请求同时预约同一资源同一时段 | 最多一笔有效预约，其余有明确冲突结果 |
| 联合申请里一项资源已占用 | 不留下其余资源的部分占用 |
| 相接时段与真实重叠 | 按统一半开区间规则得到正确结果 |
| 用户提交与网络重试 | 相同请求 ID 返回同一结果；不同内容复用 ID 被拒绝 |
| 审批与超时/取消同时发生 | 状态合法、资源不重复释放，审计可追踪 |
| 管理员更新外部占用 | 与预约提交使用相同锁协议，已有冲突进入显式处理流程 |
| RabbitMQ 暂不可用、生产者重启、消息重投 | Outbox 可恢复；消费者去重；失败可查可重试 |
| 候补通知后用户未确认 | 暂占过期释放，继续按已定义策略处理队列 |
| 学生查看他人申请、管理员跨管理范围操作 | 后端拒绝访问，并保留必要日志 |
| AI 时间有歧义、资源不存在、使用旧查询结果 | 追问/校验或重新查询，提交不绕过业务规则 |
| iOS/Android 网络中断与刷新 | 以服务端为准恢复状态，避免重复提交和错误成功提示 |
| 重复导入、空值、不同覆盖范围 | 不误删资源，不把未知状态当空闲，保持来源信息 |

并发、事务与锁测试连接真实 MySQL；替代数据库不能证明相同锁行为。消息重试连接真实 RabbitMQ。测试记录并发数、硬件、数据规模、成功/冲突/失败数和响应时间；AI 验证保留人工核查结果，避免把模型自评分当唯一依据。

公共模块仅放接口契约、错误码和少量稳定通用能力。业务实体、Mapper 和表由所属服务管理。源码、依赖锁文件、数据库迁移和部署模板进入 Git；凭据通过环境变量或私有配置注入。

## 10. 下一个具体交付

先完成一张需求确认表与一个最小验证工程。需求确认表优先解决：资源开放范围、外部占用数据来源、跨部门审批、暂占期限、候补规则。验证工程通过后，冻结依赖并开始用户/资源/预约数据库与 API 设计。
